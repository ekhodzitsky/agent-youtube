# Application migration qualification

Historical 2026-10-29 comparison. Source 0.15.0 later refreshed syom alone;
see the [current upgrade qualification](../../docs/syom-upgrade.md). The original
decision and measurements below retain their dated scope. The historical runner
now refuses a changed production pin before creating experimental files instead
of silently applying obsolete string replacements to current source.

Decision: **retain the production forks**. The pinned upstream sources plus our
patches compile and pass the application tests exercised here, but this is not
a transparent replacement for existing jobs. No production dependency, package
version, media backend or checkpoint format was changed by this qualification.

## Reproduction and scope

```sh
python3 tools/qualify_codec_migration.py \
  --source /path/to/short-recording.m4a \
  --source /path/to/long-recording.m4a
```

Requires Linux, `/usr/bin/time`, the normal Rust build environment and read-only
sibling repositories with the exact commits named in [the patch handoff](README.md).
All snapshots, binaries, media, checkpoints and logs stay under an owned, ignored
`runs/codec-migration-*` directory. The runner builds sequentially using owned Cargo target directories, copies
test executables, and never changes sibling sources.
The candidate gets an explicit experimental media-backend identity. Its lockfile
changes syom 0.7.1 to 0.8.1 without adding a runtime package.

The probe generates seven shared stereo AAC-LC recordings (two seconds plus
13 samples at 8/16/22.05/24/32/44.1/48 kHz) and one ten-minute synthetic recording.
Optional real recordings are copied and identified by SHA-256. Each build fully
decodes the same bytes, then stops at a persisted one-second checkpoint and
resumes in a separate process. Full and resumed PCM16 hashes must match within
each build. Both output lengths must match across builds. Differences between
builds are measured rather than treated as evidence of better or worse ASR.
No real speech recognition or new YouTube download is performed by this probe.

[Numeric evidence](migration-results.json) contains input/output hashes, lengths,
peak RSS, sample differences and check outcomes, without audio or transcripts.
Measurements are single Linux x86_64 debug-build observations; some processes
ran concurrently. Timings are retained for reproducibility, not a speed ranking.
RSS includes the Rust test process. The corpus does not establish universal
codec compatibility, bounded memory at arbitrary durations, or ASR accuracy.

## Observed results — 2026-10-29

All ten inputs completed in both builds, with equal sample counts. All twenty
same-build process-restart comparisons produced identical complete PCM hashes.
Seven of ten inputs differed between builds.

| Input | Decoded seconds | Cross-build PCM | Peak full-decode RSS, baseline / candidate |
| --- | ---: | --- | ---: |
| Seven synthetic rates | 2.000–2.002 each | Five differ; maximum delta 18 PCM16 units | 26.7–28.2 / 27.8–29.4 MiB |
| Synthetic long | 600.000 | Identical | 27.0 / 27.4 MiB |
| Real short | 52.965 | Differs; maximum delta 1,445 PCM16 units | 26.7 / 28.8 MiB |
| Real long | 1,053.838 | Differs; maximum delta 1,692 PCM16 units | 28.8 / 29.0 MiB |

These differences do not establish which implementation is more correct or how
recognition changes. The real inputs are retained recordings from earlier
qualification, not generated by either compared build. Both recorded real
lengths also match the earlier recovery evidence for the same source hashes.

The production gates passed: fmt, Clippy and 329 tests (14 opt-in tests ignored).
The candidate passed 244 library and 71 pipeline tests; its CLI suite, MSRV and
other platforms were not separately qualified. The strict cross-build old-job
probe failed for the bookkeeping mutations below. That failure is part of the
result and is not hidden by the passing default test suites.

## Compatibility findings

Cross-process restoration produces the complete uninterrupted output within each
build. New upstream processing changes PCM for some inputs despite identical
output duration. Keep a distinct backend identity: using an old identity would
allow mixing implementations within an existing job. Published checkpoint APIs,
cross-version state policy, release/MSRV/platform qualification and real ASR
acceptance remain prerequisites for adopting a published replacement.

The strict old-job test receives `checkpoint_settings_mismatch` with
`retryable: false` and `preserved: true`. Saved media, raw ASR and checkpoint data
remain unchanged, and the original build can still finish the job. However,
`job-control.json` changes and four preflight log files are added before refusal.
Therefore the stronger promise of an unchanged job directory **fails**. The
opt-in regression deliberately retains this failing assertion. Move the backend
compatibility check before mutable invocation setup to satisfy that promise;
completed-transcript reuse and locking must remain correct when doing so.

The runner records this refusal-test failure, continues the other checks, then
returns nonzero if any check failed. A successfully completed measurement run is
not a migration approval. Default repository tests skip the environment-dependent
migration probes; run the command above to exercise them.

## Follow-up in 0.3.13

The early-backend validation fix closes the old-job directory mutation finding.
Both the default regression and the cross-build refusal probe now pass. Completed
transcript reuse across backends also passes. See the newer
[release qualification](../../docs/release-readiness.md). The measurements and
failed immutability result above describe the original 0.3.12 experiment; PCM
differences and the remaining codec migration prerequisites are unchanged.
